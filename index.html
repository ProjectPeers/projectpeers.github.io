PEERS

Peer Evaluation System

A web platform where professors manage peer evaluations in team-based courses. Our capstone team turned the inherited application into a tested, containerized and continuously delivered product.

See the pipeline View on GitHub

What PEERS does

Professors use PEERS to collect honest feedback from the members of a team, then review it in one place.

  • Rosters and teams

    Professors create courses, manage student rosters and assign students to teams.

  • Email invitations

    Students are invited by email to evaluate their teammates.

  • Reports

    Professors receive structured reports with both numeric and written feedback.

Credit where it is due: PEERS is a continuation of an earlier KSU senior capstone project, and the application itself was built by that team (original repository). Our team's work is everything that makes it production-ready.

Our project: productionizing PEERS

The focus is not new features. It is turning the inherited app into a professionally engineered product.

What we set out to do

  • Assess the inherited architecture, tech stack and test coverage
  • Build a full automated testing pyramid: unit, integration, functional regression and end-to-end tests
  • Containerize the app with Docker and Docker Compose, with a repeatable local setup
  • Run Continuous Integration with quality gates on every pull request
  • Run Continuous Delivery to a staging environment on Render, with smoke tests
  • Keep a Requirements Traceability Matrix that links requirements to automated tests
  • Document the architecture, testing strategy, Docker setup and release procedures

Out of scope

  • Redesigning the user interface
  • New application features
  • Replacing the tech stack
  • A commercial production hosting environment
  • Migrating databases

From pull request to release

Every change reaches main through a pull request. The pipeline checks it, ships it to staging and verifies the result. Production is the one step a person approves.

  1. 1

    Pull request

    A developer opens a pull request into main. Direct pushes are rejected.

  2. 2

    Continuous Integration

    GitHub Actions builds the app and runs static analysis, unit, integration and end-to-end tests, a container check, and security scans (CodeQL and OWASP Dependency-Check).

  3. 3

    Quality gate

    Eight required checks must pass and the branch must be up to date before a merge is allowed.

  4. 4

    Deploy to staging

    After a merge, Continuous Delivery deploys the exact commit that CI tested to staging on Render and waits until each service reports it.

  5. 5

    Smoke tests and release candidate

    Smoke tests run against staging. Only if they pass does the pipeline record a release candidate. A failed deploy rolls back automatically.

  6. 6

    Production approval

    By design, a person approves: the sponsor or the team leader signs off before anything is promoted.

Staging uses a test inbox, so no real student ever receives an email from it.
